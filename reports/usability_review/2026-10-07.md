# Application usability review

Date: October 7, 2026

The main usability problem is the yearly-planning workflow. Users must understand several screens, separate sets of athlete settings, and internal schedule terminology before they can confidently create or update a year. The existing safeguards are valuable; the interface should make those safeguards easier to understand and use.

## Scope and evidence

Reviewed the current local UI source for navigation, Dashboard, Plan, Seasons, setup, event editing, proposal review, overlap handling, coaching, settings, and Help. Visually inspected seven saved desktop/mobile screenshots under [workout-removal evidence](../workout_removal/README.md), including Plan, yearly setup, events, proposals, Seasons, and Dashboard.

This is a source and saved-screenshot review, not a fresh interactive usability test. The shell could not initialize, no browser surfaces were available, and the native computer-use connection was unavailable. No live database was accessed, no schedules or application code were changed, and no tests were run. The screenshots use synthetic sandbox data; findings are tied to current source wherever possible. User confusion and likely friction below are review judgments, not measured user-test results.

## Findings, in priority order

### 1. High: Yearly planning has several entry points and names

**Evidence:** Navigation exposes Plan and Seasons as peers. Plan calls the selection a yearly plan, Seasons calls it a season, and review calls it a season schedule. The main screen explains which page owns which task rather than presenting a complete task flow. See [layout.py](../../src/garmin_data_hub/ui_nicegui/layout.py), lines 8–20; [pages.py](../../src/garmin_data_hub/ui_nicegui/pages.py), lines 1888–1928; [seasons.py](../../src/garmin_data_hub/ui_nicegui/seasons.py), lines 401–431.

**User impact:** A user opening Plan to create a year is redirected conceptually to Seasons, then back to Plan or Dashboard. The wording invites questions such as whether a season and a yearly plan are different objects.

**Recommendation:** Make Plan the primary planning destination. Provide Year overview, Events, Settings, and Workouts within the selected yearly plan. These can reuse existing pages and services initially; a storage rewrite is unnecessary. Use Yearly plan consistently in user-facing text. Put single-event planning in a distinct selectable mode, with its own settings and clearly stated scope.

### 2. High: Required setup is split across dialogs, with conflicting labels

**Evidence:** The season editor labels LTHR optional for every method, then says 80/20 requires a measured running LTHR and confirmation in preview settings. MAF adjustment and confirmation appear only in the generation dialog. The Complete preview settings action opens that generation dialog, although missing weekly minutes must be entered in Edit season. See [seasons.py](../../src/garmin_data_hub/ui_nicegui/seasons.py), lines 101–113 and 250–306; [yearly_workflow.py](../../src/garmin_data_hub/ui_nicegui/yearly_workflow.py), lines 57–61.

**User impact:** Saving setup does not mean the plan is ready to preview. A button promising to complete settings may take the user to a dialog that cannot edit the missing input.

**Recommendation:** Use a guided setup sequence: year and dates → availability and starting load → training method and required intensity settings → optional events → review. Show only the selected method's fields. Label running LTHR required for 80/20 and optional for Maffetone. Explain LTHR and MAF in plain language. Keep incomplete drafts supported, but show exactly what remains and make the action open the relevant fields directly.

### 3. High: Review summarizes database operations rather than understandable changes

**Evidence:** The saved proposal screenshot shows 102 additions, 102 removals, and 102 replacements simultaneously. The source counts additions/removals alongside replacement pairs. The expanded change table combines preserved, added, and removed rows, then sorts by date; unchanged January rows appear before the February changes. Technical reasons such as outside_range are displayed directly. See [season_review.py](../../src/garmin_data_hub/ui_nicegui/season_review.py), lines 27–44.

**User impact:** Users can interpret one set of changed workouts as several different sets of changes. The first table page does not show the changes they are being asked to approve.

**Recommendation:** Lead with a plain-language summary: Changed workouts: 102. Unchanged workouts: 263. Affected dates: Feb 1–May 30. Show replacements as one before/after row, and distinguish truly new or removed workouts separately. Default the table to changed workouts; make unchanged workouts an optional filter. Translate reasons to phrases such as Outside the affected dates. Keep the full technical diff available under details.

### 4. High: Selected-plan context is inconsistent across the Dashboard and coaching

**Evidence:** The Dashboard's timeline receives season_id, but dashboard_data receives no selected-plan identifier. Its Plan sessions count and Upcoming plan query read every active planned workout. The headline HR values also come from global athlete metrics, although yearly settings store their own inputs. Coach loads single-event settings through load_plan_settings and has no yearly-plan argument. Navigation carries season_id only to Dashboard, Plan, and Seasons. See [pages.py](../../src/garmin_data_hub/ui_nicegui/pages.py), lines 1210–1246; [data.py](../../src/garmin_data_hub/ui_nicegui/data.py), lines 228–266; [workspace.py](../../src/garmin_data_hub/ui_nicegui/workspace.py), lines 341–382; [layout.py](../../src/garmin_data_hub/ui_nicegui/layout.py), lines 54–58.

**User impact:** A user viewing a future year can see that year's timeline alongside counts or upcoming workouts from other schedules. Moving to Codex Coach can present a different event and athlete settings without a clear transition.

**Recommendation:** State the scope of every planning card. Either filter planning metrics and upcoming workouts to the selected yearly plan or explicitly label them All schedules / Upcoming across all plans. Show which athlete thresholds apply to the selected plan. Label Coach as single-event generation until yearly context is explicitly supported, and display the event/date range being used before generation. Do not silently merge the two settings systems.

### 5. High: Help teaches a different planning workflow

**Evidence:** Help's numbered instructions direct users to configure an event on Plan, generate through offline baseline or Codex Coach, and review in Codex Coach. They omit Seasons and the current yearly-proposal lifecycle. See [pages.py](../../src/garmin_data_hub/ui_nicegui/pages.py), lines 100–158.

**User impact:** A user seeking help for yearly planning is guided into single-event settings and a different proposal process.

**Recommendation:** Provide separate short Yearly plan and Single-event plan guides. The yearly guide should demonstrate setup → optional event → review → apply → subsequent event edit → review changes. Add this same sequence as contextual guidance at first use.

### 6. Medium: Multiple actions compete at each yearly state

**Evidence:** Seasons can show Complete preview settings or Review yearly proposal together with Preview yearly schedule. Edit season, Workout protection, and Archive season sit in the same action area. Plan always exposes Remove older workouts, even when the selected year is up to date. See [seasons.py](../../src/garmin_data_hub/ui_nicegui/seasons.py), lines 419–431; [yearly_workflow.py](../../src/garmin_data_hub/ui_nicegui/yearly_workflow.py), lines 33–61; [pages.py](../../src/garmin_data_hub/ui_nicegui/pages.py), lines 1923–1928.

**User impact:** Users must decide whether review and preview perform the same task and whether older-workout removal is a normal setup step.

**Recommendation:** Show one primary action for the current state: Finish setup, Review initial plan, Review changes, or Resolve conflicts. While preparing, show progress; when current, prioritize View workouts or Edit events. Move manual regeneration, protected-workout overrides, archive, and older-workout management to secondary menus or relevant conflict flows.

### 7. Medium: Race-free yearly planning raises expectations the current engine does not meet

**Evidence:** Plan prominently says no race required. Setup includes a disabled Always ready for field, with forthcoming distance-goal text repeated in summaries and proposals. The scheduling engine uses MAINTENANCE outside event influence; the workflow plan records Y5b baseline cycles and distance goals as pending. See [seasons.py](../../src/garmin_data_hub/ui_nicegui/seasons.py), lines 108–109 and 415; [season_schedule.py](../../src/garmin_data_hub/services/season_schedule.py), lines 199–225; [workflow plan](../../YEARLY_PLAN_WORKFLOW_PLAN.md).

**User impact:** A user expecting an event-free year of Base/Build/recovery cycles encounters maintenance training and an unavailable goal selector. This is a capability gap as well as a presentation issue.

**Recommendation:** Clearly describe the current race-free output as general-fitness maintenance training. Remove the disabled future feature from the main setup form and keep planned features in release information. Functional baseline cycles and distance goals need the already planned Y5b implementation; wording changes alone cannot deliver them.

### 8. Medium: Year setup defaults to a rolling range rather than a calendar year

**Evidence:** New season defaults to today through 365 days later and asks for a name and timezone as free text. It has no year picker. See [seasons.py](../../src/garmin_data_hub/ui_nicegui/seasons.py), lines 85–95.

**User impact:** Yearly planning requires users to calculate and enter calendar boundaries and an IANA timezone identifier.

**Recommendation:** Start with a calendar-year choice, automatically name the plan and fill Jan 1–Dec 31. Support Start today for the current year and Custom dates for a season spanning years. Offer a friendly timezone selector with the detected timezone preselected. Keep deliberate cross-year planning available.

### 9. Medium: Event editing exposes too many decisions at once

**Evidence:** The event form shows finish-time target, pace target, estimated completion minutes, status, terrain, taper, recovery, and course notes simultaneously. Pace is always per kilometre even though Settings can select miles. C-event guidance says taper overrides are disabled conceptually, but the taper input remains displayed. See [seasons.py](../../src/garmin_data_hub/ui_nicegui/seasons.py), lines 155–191; [pages.py](../../src/garmin_data_hub/ui_nicegui/pages.py), lines 3738–3756.

**User impact:** Finish time and completion minutes look redundant. Users can enter incompatible targets or spend time on controls that do not apply to their chosen priority.

**Recommendation:** Begin with name, date, distance, and priority, with short A/B/C explanations. Reveal goal fields after choosing Finish comfortably or Aim for a time. Use one target-type choice, Time or Pace. Put estimated participation duration in its relevant context and taper/recovery overrides in Advanced options. Disable or hide inapplicable taper controls for C events. Respect display units while converting to the existing canonical storage format.

### 10. Medium: Daily use is dominated by tables and whole-year totals

**Evidence:** Plan counts len(schedule) as Sessions, including schedule rows for rest days, and leads with start/end/strength totals followed by a wide grid. On the inspected 390px screenshot, the yearly introduction and navigation fill most of the first screen before workouts appear. The Dashboard similarly stacks lifetime and threshold cards above the yearly timeline and upcoming plan. See [pages.py](../../src/garmin_data_hub/ui_nicegui/pages.py), lines 1217–1281 and 2420–2464; [layout.py](../../src/garmin_data_hub/ui_nicegui/layout.py), lines 90–117.

**User impact:** What should I do today? is harder to answer than How many schedule rows exist? Raw phase/intensity codes and horizontal scrolling add friction.

**Recommendation:** Put Today and This week near the top, with previous/next week controls and Jump to today. Offer a readable week/list view on small screens and retain the grid for detailed analysis. Show running sessions, strength sessions, and rest days separately. Translate phase/intensity identifiers into readable labels and expand abbreviations such as TSS on demand.

## Recommended experience

Use a persistent selected-year header with the plan name, dates, and current state. Within that plan, expose Overview, Events, Settings, and Workouts. Use a clear state/action pairing:

| State | Message | Primary action |
| --- | --- | --- |
| Incomplete draft | Finish training settings before creating workouts. | Finish setup |
| No active schedule | Your settings are saved. Workouts have not been applied. | Review initial plan |
| Preparing | Preparing changes from your latest saved settings. | Progress indicator |
| Changes pending | Your event is saved. Workouts still use the previous plan. | Review changes |
| Blocked | Name the blocking event or overlap and the available resolution. | Resolve conflict |
| Current | Your workouts match your saved settings and events. | View this week |

For proposals, show why the change was prepared, affected dates, mutually exclusive change counts, weekly-load changes, and blocking issues before the detailed tables. Use Apply changes as the acceptance action and Review later as the dismissal action. Explain that Review later retains the saved event/settings changes while leaving active workouts unchanged. Preserve explicit review, acknowledgments, stale-proposal checks, and protection of completed/history/locked workouts.

## Implementation order

1. Correct conditional required-field labels, route missing settings to editable controls, and update Help to include yearly planning.
2. Simplify proposal counts, put changed workouts first, translate technical reasons, and make the primary action depend on state.
3. Make selected-plan scope explicit across Dashboard and Coach; group planning entry points and keep single-event mode distinct.
4. Add year-based setup defaults, progressive event fields, and Today/This week views.
5. Deliver baseline cycles and background distance goals as the separate Y5b feature milestone.

## Verification when changes are implemented

Walk through creating a year with no events, creating an 80/20 year with missing LTHR, and creating a Maffetone year. The missing-input action should let the user enter every named missing field. Add/move/remove an event, postpone review, reload, and confirm the saved event versus active workout distinction stays clear. A replacement should appear once in the main summary and show before/after details. Switch between two years and verify each card's stated scope; open Coach and verify its event context is explicit. Exercise an older-workout overlap and show only available resolutions. Repeat the main flows at desktop and 390px, with keyboard navigation and readable labels.

These are proposed validation tasks, not checks performed during this review.
